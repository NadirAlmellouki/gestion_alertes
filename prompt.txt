# PR1 — FIN D'APPEL VOIP SYNCHRONISÉE

Il existe un problème avec les appels manuels du superviseur.

Actuellement :

- superviseur raccroche depuis le navigateur → l'appel est correctement terminé chez l'OPS ;
- mais si l'OPS raccroche depuis MicroSIP → l'application du superviseur peut rester dans l'état "appel en cours" ;
- l'enregistrement peut également continuer alors que l'appel est terminé.

Corrige toute la chaîne :

MicroSIP
→ Asterisk
→ ARI/events
→ backend
→ WebSocket/frontend
→ SIP.js
→ interface superviseur
→ enregistrement.

Le système doit avoir une véritable synchronisation bidirectionnelle.

Cas obligatoire :

### Superviseur raccroche

Navigateur
→ SIP.js
→ Asterisk
→ MicroSIP raccroché
→ bridge détruit
→ recording arrêté
→ session clôturée
→ frontend idle.

### OPS raccroche

MicroSIP
→ Asterisk détecte le hangup
→ bridge détruit
→ recording arrêté
→ backend met à jour la session
→ événement frontend
→ navigateur revient automatiquement à l'état idle.

Ne fais pas simplement un refresh frontend.

# PR2 — ESCALADE ET VALIDATION DES ÉTAPES DE ROUTAGE

C'est un problème majeur.

Le moteur de routage peut définir par exemple :

Étape 1 :
TAM → appel

Si aucune prise en charge :
attendre 5 minutes

Étape 2 :
Admin technique → appel

Puis éventuellement :

Étape 3 :
responsable/périmètre supérieur

etc.

Le problème actuel est que l'escalade semble continuer même lorsque la première personne a répondu.

Exemple :

TAM répond à l'appel.

Malgré cela :

5 minutes plus tard → étape 2 déclenchée.

C'est incorrect.

Il faut analyser précisément la notion de :

- appel déclenché ;
- appel sonné ;
- appel répondu ;
- appel refusé ;
- appel manqué ;
- appel impossible ;
- appel terminé ;
- notification envoyée ;
- notification prise en charge ;
- incident résolu.

Attention :

"appel répondu" ne signifie pas forcément que l'incident est résolu.

Analyse donc le modèle métier existant et ne mélange pas :

- notification envoyée ;
- notification reçue ;
- notification acceptée/pris en charge ;
- incident résolu.

Pour les appels VoIP, la réponse réelle de l'OPS doit pouvoir être utilisée comme événement de prise en charge selon la logique métier prévue.

Pour Email/SMS/Kafka, ne suppose pas qu'une réponse téléphonique existe.

Il faut déterminer comment le système doit décider de continuer ou d'arrêter l'escalade selon les mécanismes réellement disponibles.

Analyse également :

- scheduler ;
- délais ;
- conditions ;
- statut des notifications ;
- événements ;
- concurrence ;
- idempotence ;
- retries ;
- escalade déjà déclenchée ;
- conditions de résolution Dynatrace.

Corrige l'architecture si nécessaire.

# PR4 — JOURNALISATION ET INFORMATIONS DESTINATAIRES

Les logs existent déjà mais certaines informations sont trop techniques.

Exemple actuel :

- extension SIP ;
- numéro ;
- cause = null ;
- SIP status = ANSWERED/HANGUP/FAILED.

Il faut produire une journalisation compréhensible.

Au lieu d'afficher uniquement des variables brutes, construire une description métier claire.

Exemple de principe :

"Appel VoIP vers Ahmed X (Admin technique — Solution Y) répondu après 12 secondes."

ou :

"Appel VoIP vers Ahmed X échoué : le destinataire n'était pas joignable."

Le champ `cause` est actuellement souvent `null`.

Diagnostiquer pourquoi.

Ne pas simplement remplacer `null` par une chaîne arbitraire.

Déterminer les véritables causes disponibles depuis :

- Asterisk ;
- SIP ;
- backend ;
- exceptions ;
- timeout ;
- absence de registration ;
- hangup ;
- busy ;
- failed ;
- no answer.

Associer également les informations métier du destinataire :

- nom ;
- rôle ;
- solution ;
- téléphone ;
- extension si pertinente.

Les logs doivent rester exploitables pour l'audit.

# PR6 — COHÉRENCE ENTRE ALERTES, CONTACTS ET DISPONIBILITÉ

Il existe plusieurs incohérences.

Par exemple :

- "Dernier contact" reste vide après un contact ;
- les compteurs succès/échec VoIP peuvent être incohérents ;
- un destinataire non joignable peut encore être appelé ;
- l'état de disponibilité n'est pas correctement pris en compte.

Analyser le cycle de vie réel d'un destinataire.

Un utilisateur marqué comme non joignable/hors service ne doit pas être automatiquement appelé comme s'il était disponible.

Mais attention :

ne mélange pas :

"destinataire SIP non joignable"

avec :

"destinataire a répondu mais n'a pas réellement traité l'incident".

Ce sont deux situations métier différentes.

Le système doit distinguer :

- disponible ;
- non enregistré ;
- occupé ;
- non joignable ;
- timeout ;
- appel répondu ;
- appel refusé ;
- appel terminé ;
- prise en charge ;
- incident résolu.

Vérifier également les mises à jour de :

- dernier contact ;
- dernier appel ;
- dernier succès ;
- dernier échec ;
- compteurs ;
- statut de notification ;
- historique.

# PR8 — ALERTES PAR UTILISATEUR ET TRAITEMENT SUPERVISEUR

L'interface actuelle doit mieux distinguer les alertes nécessitant une intervention.

Je préfère éviter de multiplier inutilement les pages.

Analyser la possibilité de conserver :

- une page "Alertes" ;
- une page "Historique" uniquement si elle apporte réellement une différence utile.

Les filtres doivent permettre notamment :

- mes alertes ;
- alertes à traiter ;
- alertes traitées par moi ;
- alertes non prises en charge ;
- alertes escaladées ;
- alertes résolues ;
- période ;
- criticité ;
- solution ;
- statut.

### Superviseur

Le superviseur doit pouvoir identifier rapidement une alerte nécessitant une intervention manuelle.

Depuis le détail d'une alerte, il doit pouvoir voir les responsables pertinents.

Par exemple :

- TAM de la solution ;
- administrateur technique de la solution ;
- responsable du domaine ;
- responsable du pôle ;
- responsable de l'entité ;

uniquement lorsque ces informations existent réellement dans le référentiel.

Le superviseur ne devrait pas devoir parcourir une liste globale de centaines de personnes pour trouver le responsable d'une alerte.

Depuis le détail de l'alerte, il doit pouvoir déclencher l'appel manuel vers le ou les destinataires pertinents selon la logique métier.

Analyser la meilleure UX :

bouton,
action,
popup,
liste des responsables,
etc.

### OPS

L'OPS doit également pouvoir consulter clairement les alertes qui lui sont affectées ou qui le concernent.

Afficher leur état :

- affectée ;
- notification reçue ;
- prise en charge ;
- escaladée ;
- résolue ;
- etc.

Ne crée pas des pages supplémentaires si des filtres ou une vue adaptée permettent de résoudre proprement le problème.

# PR9 — MODÈLE ORGANISATIONNEL ET ROUTAGE

Il existe actuellement une confusion dans le moteur de routage.

La hiérarchie métier doit être respectée.

Un TAM est lié à une SOLUTION.

Il ne doit pas être considéré comme un manager de domaine.

Commencer avec les niveaux réellement nécessaires au routage actuel :

- TAM de solution ;
- administrateur technique de solution.

Puis permettre l'escalade vers les niveaux supérieurs lorsque la conception métier le prévoit :

- responsable domaine ;
- responsable pôle ;
- responsable entité.

Attention aux solutions qui n'ont :

- pas de TAM ;
- pas d'administrateur technique ;
- ou une information organisationnelle manquante.

Le moteur doit gérer proprement ces cas.

Ne suppose pas que toutes les solutions possèdent tous les responsables.

Également :

- remplacer "directeur d'entité" par "responsable d'entité" ;
- vérifier les libellés sensibles au cas/casse ;
- analyser pourquoi la sélection de certains niveaux organisationnels provoque actuellement une erreur HTTP 500 lors de la sauvegarde ;
- corriger la cause réelle.

Analyser également la nécessité du champ qui détermine séparément le niveau organisationnel du destinataire.

S'il est redondant avec le rôle/type de destinataire et la relation à la solution, ne conserver qu'un modèle cohérent.

Ne supprime pas ce champ uniquement parce qu'il semble redondant : vérifie d'abord son utilisation dans le moteur de routage, les règles, la BDD et le frontend.

# PR10 — DIAGNOSTIC COMPLET DU MOTEUR D'ESCALADE

Cette partie est prioritaire.

Fais une analyse approfondie de tout le mécanisme :

Routing
→ Notification
→ attente
→ vérification condition
→ décision d'escalade
→ prochaine étape
→ résolution.

Vérifie :

- modèle de données ;
- règles ;
- conditions ;
- délais ;
- scheduler ;
- événements ;
- statuts ;
- transactions ;
- concurrence ;
- retries ;
- idempotence ;
- résolution Dynatrace ;
- appels VoIP ;
- Email ;
- Kafka/SMS ;
- historique ;
- audit.

La condition d'escalade doit être réellement évaluée.

Ne déclenche jamais automatiquement l'étape suivante simplement parce que le délai est écoulé si la condition d'escalade n'est plus vraie.

Exemple :

Étape 1 → appel TAM.

Si TAM répond :

→ enregistrer l'événement de prise en charge selon la logique métier
→ arrêter l'escalade.

Si TAM ne répond pas :

→ attendre le délai configuré
→ vérifier l'état réel
→ si condition toujours vraie → étape suivante.

Si l'alerte Dynatrace est résolue :

→ arrêter l'escalade.

Le délai de vérification ne doit pas être arbitraire.

Il doit provenir de la configuration métier existante ou être explicitement configurable.

Analyse le fonctionnement actuel de la vérification Dynatrace et conserve l'API appropriée déjà prévue par le projet.
